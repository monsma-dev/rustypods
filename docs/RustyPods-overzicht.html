RustyPods

A systemd-native pod runtime for Linux — nspawn pods on Btrfs, driven by one Rust daemon over a Unix socket and gRPC.
Technical overview · 27 September 2026 · Nick Monsma

1. In one paragraph

RustyPods is a pod orchestrator that uses systemd-nspawn as its isolation primitive instead of the classic container stack. There is no containerd, no runc, no overlayfs, and no Docker daemon. One Rust daemon (rustypodsd) talks directly to systemd, machined, Btrfs and nftables through zbus. On top of that local machine model it adds the pieces a second site actually needs: a private mesh CA, mutual TLS between nodes, a WireGuard fabric, an availability policy, and a Raft election whose vote is on disk before it is sent. Business data stays in the database that already owns it. Raft is reserved for membership and, later, the desired set of pods.

2. The problem it solves

The dominant container stack is layered and heavy: Docker, then containerd, then runc, then kernel namespaces, plus overlayfs for storage and a separate network layer. Kubernetes adds a scheduler, an API server, etcd and a control plane. That is proven at large scale, and it is the wrong price for one machine or two sites:

  • A single host, or a pair of hosts, pays an operational cost that belongs to a much larger cluster.
  • Every layer is its own failure domain, its own CVE surface and its own configuration language.
  • systemd-nspawn has done the core job for years — a bootable machine on the host kernel, registered with machined, limited by a cgroup scope — and it still has no management layer: no images, no snapshot workflow, no exec model, no port publishing, no second site.

RustyPods is that missing layer, and it stays small on purpose. The daemon is one process. State is a directory. Firewall rules are one readable nftables table. A second site is a peer and, when two hosts are not enough to vote, a witness. It is not a new etcd.

Dataplane without a proxy

Host-to-pod data uses real shared pages. /dev/shm/rustypods/<pod>/ is bound to /run/rustypods/shm/ inside the pod. An mmap there is kernel shared memory: no socket and no copy. The daemon also binds /var/lib/rustypods/run/<pod>/agent.sock into the pod as the control channel.

Podman is a good tool, and it brings the OCI runtime with it: runc, conmon, netavark, and on a rootless host often fuse-overlayfs. It models a container as a process. RustyPods models a pod as a machine. machined knows it. cgroup limits come from systemd. Stopping it is a signal to systemd-PID 1 inside the pod. There is no conmon per container and no overlayfs mount stack.

Kubernetes schedules hundreds of nodes. RustyPods is aimed at the operator who currently runs a VM, Compose, and a handmade tunnel. The mesh gives pod addresses on a second site without bootstrapping a cluster first. Scheduling stays opt-in: a stack with no placement rule remains on the host where it was created.

6. Security model

The exec path is deliberately stricter than most tools in this class. The rule is that no image binary ever runs at a higher privilege than the target identity.

  • Identity changes happen in the daemon (pre_exec_identity, async-signal-safe calls) or inside nsenter. Image binaries such as setpriv or su are never used to raise privilege on the host.
  • PR_CAPBSET_DROP removes every capability outside the nspawn bounding set. Pods without a user namespace also set PR_SET_NO_NEW_PRIVS.
  • Root exec in a pod without a user namespace is host root. It is refused unless the operator passes --user root. Those pods are trusted code only.
  • Exec'd processes enter the pod cgroup atomically through nsenter --cgroup. MemoryHigh and CPUQuota apply to exec work. A cgroup v2 kill covers the group when a timeout fires.
  • A publish without a host IP is loopback-only. Pod egress and published ports use RustyPods' own nftables table. Pods cannot reach each other's unpublished ports, and the host-loopback pattern behind CVE-2020-8558 is closed.
  • Writable binds of /run, /etc, /usr, /boot, /proc, /sys, /dev and /var/lib/rustypods are refused. A writable bind of /run/user once wiped a real login session; that class of mount does not come back.
  • Rootfs setup uses openat2 with RESOLVE_BENEATH so a pod cannot escape its tree through a symlink.
  • rustypods-proto, rustypods-client, rustypods-agent and rustypods-ingress forbid unsafe code. The daemon and the CLI use unsafe only for libc, ptys and ioctl.

Mesh certificates

Once a packet leaves the host, a shared cluster token is not the gRPC credential. The mesh CA is name-constrained to node.mesh.rustypods and to fd00::/8, with a path length of zero, so a node certificate cannot sign anything else. A node certificate lasts seven days, carries server and client EKUs, and names both a DNS SAN derived from the WireGuard public key and the host ULA. The listener inserts that identity only when the certificate's IPv6 SAN equals the TCP source. A peer cannot request a vote under another node's name.

ca.key is mode 0600 and never leaves the root. node.key is mode 0640 and is shared with the administrator group so rustypods --host can present it. Group-writable or world-readable keys are refused. A leaf directory (ca.crt, node.crt, node.key, and no ca.key) is accepted as-is and is not rotated in place. Anything between empty and a full root or leaf is corrupt, and the daemon will not mint a CA over it.

Certificate bootstrap stays on the local socket. mesh create-csr prints the WireGuard public key and a CSR. mesh sign-csr discards every name in that CSR and stamps the WireGuard identity itself. The mesh listener refuses both calls. A witness with an empty mesh-pki cannot run mesh init: a witness does not mint a CA and must join through create-csr.

The four PKI files are one directory swap

Linux rename cannot replace a directory that already has entries. RustyPods therefore writes the complete set into .mesh-pki.tmp, parks the live mesh-pki as .mesh-pki.bak, and renames the staging directory into place. The backup is removed only after that rename succeeds. A crash in the middle leaves the original directory, or no directory plus the backup. The next start restores the backup and deletes an incomplete staging directory. A half-written CA is not a layout the daemon will trust.

7. Mesh without a cluster

rustypods mesh init on a host creates a WireGuard identity. The private key stays in conf/mesh.conf, mode 0600. A stable ULA /48 is derived from the public key, with the two required ULA bits forced. Peers are added on both sides with mesh add-peer. There is no mesh join over the network.

  • Each pod with a private netns receives fd<host>:<idx>::2. The host control address is fd<host>::1. Both are routed across peers, without NAT.
  • A DNS registry on the mesh resolves pod names. Records expire by TTL instead of living until a process remembers to delete them.
  • The pump is userspace WireGuard (BoringTun). Roaming updates a peer's endpoint, so a NATed host can keep the tunnel as long as it sends the first packet to a public ip:51820.
  • Gossip is HMAC-SHA256 and is chunked. The cluster token still exists for that path and for token rotation. It is not sent on mesh gRPC.
  • An nftables set accepts TCP 5306 only from peer host addresses. mTLS is the check behind that filter, not a replacement for it.
  • Handshake floods are bounded so a noisy UDP peer cannot pin the pump.

Joining a node, including a witness, is an out-of-band exchange over the SSH session that already reaches the local socket:

# on the joiner — writes node.key, does not create a CA
rustypods mesh create-csr

# on the root — local socket only; prints ca.crt, then node.crt
rustypods mesh sign-csr <wg-pubkey> joiner.csr

# operator places those two files beside node.key, never ca.key
# then, on the root, the witness is a voter and not a placement target
rustypods mesh add-peer <public-ip>:51820 <pubkey> --witness

In September 2026 a live mesh between an AlmaLinux 9.8 host and an AlmaLinux 10.2 host carried pod-to-pod traffic over the tunnel, with handshakes in both directions. That measurement is a tunnel. It is not yet a Raft quorum. A binary built on Debian 13 requires glibc 2.39 and does not run on AlmaLinux 9. The witness is intended to be a bare Debian 13 host with a public address, built on that host.

8. Availability

A Btrfs snapshot is a local copy. It dies with the disk it sits on. Four rules in ha.rs decide what a missing site means. A stack that asks for something the rules forbid is rejected at apply.

  1. Traffic. Members that share serves = "orders" are one DNS name. While quorum holds, the name points at the live primary, or at the live mesh replica when the primary's host is dead. A name with nobody left is withdrawn.
  2. Workloads. ha = "movable" may restart on the single surviving host. The default is pinned. A volume, a published port, an ingress name, or host access cannot be movable: there is nowhere for that byte or that socket to go.
  3. Databases. replicates = "snapshot" is the local time machine and is not a second copy. replicates = "mesh" means MySQL or Postgres is replicating itself across the mesh. RustyPods does not copy those rows and does not restart a database on the other host. It only retargets the name onto the replica that is already running there.
  4. Quorum. A plan is published only when a majority of voters is reachable. Two hosts need a witness. The witness votes and runs no pods. One live host out of three publishes nothing, so a partition cannot elect two leaders. Two hosts and no witness also publish nothing once one of them is gone.

is_witness is stored on the peer, in mesh.conf format 4. The planner places work only on a host. Two live witnesses can hold quorum and still receive no restart and no published address. A witness leader drops restart, DNS and stranded work locally. Single-node placement remains the default, so a shop does not have to become a cluster to keep running.

Raft, and only the vote

Raft here is the election for mesh membership. It is not a database. current_term and voted_for are the fields that must survive a crash, because a node grants at most one vote per term. They are written to raft.state, mode 0600, with an fsync before any RequestVote is sent.

The write does not run on a Tokio worker while the election mutex is held. The term and the vote are copied out, the lock is dropped, and a blocking task fsyncs the file. tokio::fs::write is not used: it reports success when the bytes are in the page cache, and a power loss can then lose them. If the fsync fails, memory is put back to the previous term, provided nothing newer landed while the write was in flight, and the vote is not sent. That is the split-brain barrier. A node must not be able to vote twice in one term after a crash.

A missed heartbeat starts an election. The timeout is 150–300 ms. A leader sends empty AppendEntries heartbeats. Quorum is a majority, counting this node. One acknowledgement is enough for three voters and not enough for five. A laptop with no peers has a majority of one and elects itself. A non-empty append is rejected. There is no stored log yet, and the daemon will not pretend an entry was committed. The availability plan is computed on a quorum and then discarded until that log carries workloads. The witness is already excluded from the decision, so the discarded plan cannot name it as a target.

The election task is tied to the mesh listener. When the listener returns or is aborted, it signals the election loop and waits for it to stop. A dead listener does not leave a second voter running beside the next one.

9. Who it is for

  • One host, or a few hosts. Homelabs, edge, and small production: anyone who currently maintains a VM, Compose, and a tunnel by hand.
  • systemd shops. Teams that already use machined or nspawn and want a real management layer.
  • A second site that must not run the shop. A witness on a small VPS, voting and holding no pods, so two application hosts can lose one without both sides deciding.
  • Not this, on purpose. A multi-tenant platform that schedules hundreds of nodes. That remains Kubernetes.

The honest boundary: the vote cannot be granted twice after a crash, a witness cannot be given a pod, and a witness cannot mint a CA. The tunnel can already carry packets. The log that would move a stack, and the witness that would make two hosts a majority, are the next cuts. They are not implied by the election that exists today.

11. Install from a terminal

Build on the machine that will run the daemon. A binary from Debian 13 needs glibc 2.39 and does not run on AlmaLinux 9. The host must boot systemd as PID 1, on cgroup v2, with machined.

On Debian or Ubuntu, install a compiler, mold, and Rust:

sudo apt install build-essential mold pkg-config curl ca-certificates
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
. "$HOME/.cargo/env"

On Fedora, the package line is sudo dnf install gcc mold pkgconf curl ca-certificates. On Arch Linux, install base-devel, mold and rustup.

git clone https://github.com/monsma-dev/rustypods.git
cd rustypods
bash scripts/build.sh
sudo bash scripts/install-daemon.sh --user "$USER"
rustypods doctor

rustypods pull docker.io/library/debian:trixie
rustypods create app --image debian-trixie --port 8080:8080
rustypods start app --memory-high 2G
rustypods ps

scripts/build.sh compiles the release binaries and runs the tests. The installer adds nftables, iproute, util-linux, btrfs-progs, socat and the nspawn package for that distro, then starts rustypodsd. Your user is the administrator of the local socket. bash scripts/install-daemon.sh --dry-run --user "$USER" prints the plan and changes nothing. sudo bash scripts/uninstall-daemon.sh removes the unit and keeps /var/lib/rustypods unless you pass --purge-data.

RustyPods is a different architecture, not another container CLI. A pod is a systemd machine on the host kernel, with the management layer nspawn never had: snapshots, an exec path with a real privilege model, a private nftables network, and a WireGuard mesh whose nodes authenticate with their own CA. Two sites can vote only when a witness is present. That witness counts, and it runs nothing. The bar is a Raspberry Pi at one end and a second datacenter at the other, without standing up a cluster to get there.
